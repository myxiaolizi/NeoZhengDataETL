## 功能特性

### 项目管理与分组

| 能力 | 说明 |
|---|---|
| **多级分组树** | 项目可按业务域分组，支持最多 5 级嵌套（`jdywh_project_groups.parent_id` 自引用） |
| **分组筛选** | 左侧分组树点击即筛选；「全部项目 / 未分组」两个内置视图；父分组计数含所有子分组 |
| **批量移动** | 卡片视图切换「批量移动」后勾选多个项目，一次性归入目标分组 |
| **分组管理弹窗** | 列表式管理全部分组，支持新建子分组、编辑、删除、全部展开/收起 |
| **安全删除策略** | 删除分组**不删除项目**，其下项目自动上移到父分组（或指定目标）；有子分组时拒绝删除 |
| **防环校验** | 移动分组时校验目标不能是自身或自身后代，避免形成环 |
| **同级唯一** | 同一父级下分组名唯一；不同层级可同名 |
| **历史分类迁移** | 升级时自动把旧的自由文本 `category` 转为正式分组，历史分类不丢失 |

> 分组相关接口：`GET/POST /api/project-groups`、`PUT/DELETE /api/project-groups/:id`、
> `POST /api/project-groups/assign`（批量移动）、`POST /api/project-groups/reorder`（排序）。
> 项目列表支持 `?groupId=<id|0|all>&includeSubGroups=1` 过滤。

## 快速开始

```bash
# 1. 安装依赖
npm install

# 2. 配置
cp .env.example .env
#   本机开发：DB_HOST=tx.zhengl.vip
#   服务器部署：DB_HOST=127.0.0.1

# 3. 启动
npm start
#   访问 http://127.0.0.1:8781
```

首次启动自动完成：建表、迁移、写入 3 个内置角色、56 项默认设置、初始化管理员账号（凭据取自 `.env`）。

### 数据库配置

```ini
DB_HOST=tx.zhengl.vip        # 本机开发；部署到服务器改为 127.0.0.1
DB_USER=jdy-push
DB_PASSWORD=your-db-password
DB_NAME=jdy-push
TABLE_PREFIX=jdywh_          # 表名前缀白名单
```

> **安全约束**：应用内置表名前缀白名单，所有建表/改表/删表操作前都会校验表名以 `jdywh_` 开头，
> 非本应用创建的表一律拒绝操作。即使误配到共享库，也不会影响其他应用的数据表。

## 使用流程

### 1. 接入数据

**方式 A：简道云推送**
1. 「数据项目」→ 新建项目（选择存储数据源）
2. 项目详情 →「推送地址」→ 复制地址
3. 简道云表单 →「扩展功能 → 数据推送 → 新建数据推送」→ 目标服务器选「自定义服务器」→ 粘贴地址
4. 简道云「生成 Secret」→ 回填到项目设置
5. 「字段设置」→「导入简道云字段表」→ 粘贴字段对照表

**方式 B：接口采集**
1. 「数据集成」→「+ 接口采集」
2. 配置接口地址、鉴权、响应数据路径、字段映射
3. 保存后点击「执行」或配置定时触发

### 2. 加工数据

「字段设置」中为字段选择解析方式 →「同步表结构」回填历史数据。

```
原始表 jdywh_data_16         解析表 jdywh_parsed_16
─────────────────────        ─────────────────────
widget_1791449342208          widget_1791449342208_p
{"_id":"65d4...",            郭晨(guochen@sinohealth.cn)
 "name":"郭晨",
 "status":1,
 "username":"guochen@..."}
```

### 3. 分析展示

1. 「数据集」→ 新建数据集（选项目解析表 / SQL / 数据表）
2. 「报表中心」→ 新建报表 → 设计器配置图表 → 保存
3. 「报表中心」→ 分享 → 生成外链（可设密码与有效期）

### 4. AI 问数

「系统设置 → AI 问数」配置接口地址与密钥 → 开启 → 在「AI 问数」页面直接提问。

## 关键设计

| 机制 | 说明 |
|---|---|
| 签名校验 | `sha1("{nonce}:{payload}:{secret}:{timestamp}")`，与简道云开发指南一致 |
| 自动建表 | 首次推送某字段自动 `ADD COLUMN`，字段名写入列注释 |
| 双表分离 | 原始值与解析值分表存储，便于对照与治理 |
| 行大小保护 | 字段较多时自动降级为 TEXT，避免 MySQL 单行 65535 字节上限 |
| 列名兼容 | 复用历史列名（`widget_xxx` ↔ `w_xxx`），避免同一字段拆成两套列 |
| 数据去重 | `jdy_data_id` 唯一索引 + `ON DUPLICATE KEY UPDATE` |
| 快速响应 | 成功返回 200；**失败必须返回非 2xx 让简道云可见**：签名不符 `403`（配置问题，不重试）、报文非法 `400`、令牌未知 `404`、处理异常 `500`（可重试）。历史实现所有失败都返回 200，导致简道云后台永远显示成功、业务方无从发现推送被拒 |
| 签名失败 | 已配置 Secret 但签名不符时拒绝写入数据（仅记日志） |
| 权限隔离 | 中间件级 `requirePerm`，前后端双重校验 |
| 表名白名单 | 所有 DDL/DROP 前校验表名以 `jdywh_` 开头 |
| SQL 只读 | 数据集 SQL 仅允许单条 SELECT/WITH，拒绝写操作与多语句 |
| 独立数据库 | 使用专用库 `jdy-push`，与其他业务库物理隔离 |
| 派生字段 | 字段定义新增 `source_key`，同一源字段可按路径拆出多列（地址→省/市/区、连锁名称→标题）。**推送与回填都必须回落到 `source_key` 父字段取值**——派生字段自身的 `field_key`（形如 `_widget_xxx#province`）不存在于推送报文 |
| 流程运行态同步 | 流程推送**只**维护「当前节点 / 当前负责人」两个字段，回写到表单解析表；**不再触碰 8 个节点时间列**（见下节） |
| 变更描述 | 每条接收日志都记录 `change_summary`，用自然语言说明本次改了哪些字段、从什么变成什么 |
| 多值列分隔符 | 数组字段拼接统一用**英文逗号** `,`（与业务系统导出口径一致） |

## 流程推送与表单推送的分工

业务系统的「新增智能体签约」解析表，由两个推送项目共同维护：

| 字段类别 | 归属项目 | 说明 |
|---|---|---|
| 表单字段（区域、连锁名称、流水号、**8 个节点时间列**等） | **CRM表单推送**（`crm`，项目 16） | 简道云「数据推送」→ `data_create/update/remove`，时间列按 `parse_mode=timestamp` 解析 |
| 流程运行态（当前节点、当前负责人） | **CRM流程推送**（`crm_2`，项目 102） | 简道云「流程推送」→ `task_update`，回写 `flow_current_node` / `flow_current_owner` |
| 更新时间 | 两者都有 | 用于交叉校验数据新鲜度 |

### 节点完成时间的判定口径（2026-10-28 修订）

**结论：8 个节点时间列 = 简道云表单「时间自动化」字段原值，不是流程事件的完成时间。**

历史实现（`src/flow-ingest.js` 的 `syncRunStateToFormProject`）会用流程事件聚合出的完成时间覆盖这 8 列，
并按「当前节点截断」清空当前节点及之后的列。经 2026-10-28 与业务表逐格对账，该设计有三处错误：

1. **命中率极低**：与业务表比对仅 26/90、19/91、6/45…；而表单原值列命中 90/90、91/91、45/45（100%）。
2. **截断规则被业务否证**：业务表中「当前节点=实施对接」的记录里，实施对接时间有值的就有 45 条，
   按截断规则该列必须为空。
3. **回退场景会清空已完成节点的时间**。

现已改为：**流程推送只写 `flow_current_node` / `flow_current_owner`，不再触碰这 8 列。**
防复发单测见 `_work/test/guard-flow-regression.js`。

### 当前节点 / 当前负责人的取值口径

- **有流程事件**（约 2/3 记录）：用流程事件聚合，`flow_name` → 归一化节点名，最新事件的
  `event_current_assignee` → 当前负责人。
- **无流程事件**（项目 102 于 2026-10-23 上线，此前事件简道云不回溯）：节点取表单字段
  `widget_1791533061604` 的归一化值；负责人按节点映射角色字段
  （实施对接→销售、客服处理→客服、客户培训→培训人、对接审核→培训人/解决方案）。
- **流程已完成**（`flowState=1`）：当前节点 / 当前负责人留空。

历史节点名归一化：`系统对接`→`实施对接`、`解决方案确认`→`对接审核`、`开通`→`策略开通`、
`使用培训`→`客户培训`、`系统测试`→`客服处理`、`客户结论`→`策略审核`。

> 流程事件的 `finish_action` 语义仍保留在 `src/flow-state.js` 供审计与追溯，
> 但**不再参与** 8 个时间列的计算。

聚合逻辑集中在 `src/flow-state.js`，与数据库无关，可单独跑单元测试。

## 已知问题与修复记录

| 问题 | 原因 | 修复 |
|---|---|---|
| 项目详情页数据明细一直显示「加载中」 | EJS 模板字面量内正则 `\/+$` 被二次转义成非法 JS | 改用 `[/]+$`；统一改为事件委托避免内联 `onclick` 引号转义 |
| 静态资源更新后浏览器仍是旧样式 | Nginx 代理缓存 | `rm -rf /www/server/nginx/proxy_cache_dir/* && nginx -s reload` |
| 字段较多时建列报 `Row size too large` | MySQL 单行 65535 字节上限 | 加入行大小守卫，超限自动降级 TEXT |
| 同一字段出现两套列 | 历史列名与新建列名不一致 | 导入时复用历史列名并校正字段定义 |
| 解析表回填 0 行 | 回填逻辑写到了原始表 | 改为 upsert 到解析表 |
| 旧项目缺少解析表名 | v2 升级遗留 | 启动时自动补齐 `parsed_table` |
| **13 个新字段全挤在「地址」一列** | `stripDupSuffix()` 把 `w_1792131264427` 末尾数字当成重复序号，削成 `w` 后互相判为同基名列 | 重写 `stripDupSuffix`：控件列为前缀 `w`/`widget`/`_widget` 时数字属控件 ID，不剥离；仅剥真正的 `_2`/`_3` 后缀 |
| **解析表比原始表多 58 行** | 2026-10-17 历史导入只写了解析表、没写原始表 | 按用户确认删除孤儿记录（备份保留 `_work/backup/`） |
| **节点时间显示回退后的值** | 聚合时未考虑流程回退 | 按「当前节点截断」重算，当前节点及之后强制留空 |
| **流程推送算不出完成时间** | 落库值 `finish_action` 是中文（提交/转交），代码只认英文 | `COMPLETE_ACTIONS` 同时收录中英文 |
| **接收日志只有原始 JSON，看不懂** | 缺变更描述 | 新增 `log-describe.js` + `change_summary` 列，历史 1308 条已回填 |
| **简道云推送经常报 `timeout of 5000ms exceeded`** | `ensureFieldColumn` 每次推送对每个字段无条件执行 `ALTER TABLE ... MODIFY COLUMN`（只为刷新中文注释），crm 项目 67 字段 × 原表/解析表 ≈ 134 条 DDL/请求，单条 18~30ms → 单请求 2.4~3 秒；并发批量提交时 MDL 排队放大到 10~37 秒 | `schema.js` 加 `sameColumnType()` 与注释比对，**类型与注释都没变就跳过 DDL**；`ensureProjectTables` 结果按项目缓存 60 秒（省掉每次 8~10 条 `information_schema` 查询）。实测单请求 2.9s → 60ms，并发 10 条 23.2s → 0.25s |

### 推送性能基准（2026-10-28 实测，crm 项目 61 字段）

| 场景 | 修复前 | 修复后 | 5 秒超时 |
|---|---|---|---|
| 单条推送（串行） | 2769~3036ms | 40~102ms | 0/5 |
| 并发 10 条（模拟批量提交） | 22897~23159ms（墙钟 23.2s） | 150~219ms（墙钟 0.25s） | 10/10 → 0/10 |
| 并发 20 条 | — | 409~520ms（墙钟 0.56s） | 0/20 |
| `syncFieldColumns` 结构同步（67 字段） | 2.9s / 134 条 DDL | 17ms / 0 条 DDL | — |

> 判定基线：简道云推送要求 5 秒内返回，超时即判失败并重试。
